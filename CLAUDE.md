# Fork overrides

This is `anno-systems/LibreChat`, a solo-maintained fork of `LibreChat-AI/LibreChat`. Everything in `AGENTS.md` applies unchanged **except** what this section replaces. Where the two disagree, this section wins. `AGENTS.md` is upstream's file and is never edited in this fork, so upstream merges stay clean.

## Branching and pull requests (replaces the dev/canary rules in AGENTS.md)

- This fork has only `main`. Branch from `main` and open pull requests against `main`. Ignore everything in `AGENTS.md` about `dev`, `canary`, `--base dev`, `--base canary`, the main-to-dev retarget workflow and the `target: main` label.
- Work done by Claude goes on a branch named `claude/<short-topic>`. Never push to `main` directly. The owner reviews and merges the pull request.
- Closing keywords such as `Fixes #N` work here, because `main` is the default branch.
- Reproduce the PR's static checks with `npm run static-checks -- --against origin/main` (use `static-checks:full` for the slower gates).
- In cloud sessions, `gh pr` and `gh issue` do not work (the GitHub proxy blocks GraphQL). Use the built-in GitHub tools for pull requests and issues.
- The review, completion, verification, module-boundary, style and testing rules of `AGENTS.md` all still apply. `/verify` runs the verification part.

## Staying close to upstream

- Prefer additive changes (new modules, new files, config) over rewriting upstream code. No drive-by reformatting, renames or refactors in files we do not otherwise change.
- Do not edit upstream's `.github/workflows`. Workflows this fork does not want are disabled in GitHub's Actions settings instead.
- Update from upstream with a merge, not a rebase: `git remote add upstream https://github.com/LibreChat-AI/LibreChat.git`, `git fetch upstream main`, `git merge upstream/main`. Upstream's `main` is a pointer to a tested `dev` commit.
- `.github/workflows/upstream-sync.yml` does this every Monday and opens a `sync/upstream` pull request, or an issue "Upstream sync needs attention" on a conflict. Merge sync pull requests with a merge commit, never squash or rebase, or the next sync cannot tell which upstream commits are already in. Cloud sessions can fetch upstream (public, read-only), so a conflict can be resolved there on `sync/upstream`.

## Platform plan

This fork is the base of a multi-tenant platform. The architecture, repositories, roadmap and open
decisions are in `docs/platform/architecture.md`. Read it before platform work and update it when a
decision changes.

## Customizations

Record every deliberate deviation from upstream here, one line each, so merges and conflicts stay explainable.

- `.github/workflows/fork-image.yml` (fork-only): on pushes to `main` (same `paths` as `dev-images.yml`) and on manual dispatch, builds `Dockerfile` target `node` for `linux/amd64` and pushes `ghcr.io/<owner>/librechat:latest` and `:sha-<short>` with `GITHUB_TOKEN` only, no Docker Hub.
- Tenant-aware OpenID (`packages/api/src/auth/openid/tenant.ts`, wired in `api/strategies/openidStrategy.js`, `api/strategies/openIdJwtStrategy.js`, `api/server/routes/oauth.js`, `api/server/controllers/auth/oauth.js`, `api/server/middleware/oauthNavigation.js`): optional `TENANT_DOMAIN_SERVER`, `TENANT_DOMAIN_CLIENT`, `OPENID_TENANT_SCOPE` and `OPENID_TENANT_CLAIM` give each tenant its own callback and redirect URLs, provider scopes, and a claim that must match the request tenant. The `openidJwt` strategy (`OPENID_REUSE_TOKENS`) checks the claim too and, with `TRUST_TENANT_HEADER`, looks the user up in the proxy's tenant. The admin login (`/api/admin/oauth/openid`, `api/server/routes/admin/auth.js`) is tenant-aware the same way, and `OPENID_ADMIN_ROLE` also matches role claims shaped as objects keyed by role (Zitadel, `packages/api/src/auth/openid/roles.ts`). The `adminPanelURL` in `/api/config` names the admin's tenant (`?tenant=`, `getAdminPanelLink`), so the admin panel can fill in the organization. With `OPENID_ADMIN_REQUIRE_MFA=true` (`packages/api/src/auth/openid/mfa.ts`) the admin login needs a second factor in the ID token's `amr` claim; a refused admin login returns to the admin panel with `error=mfa_required` or `error=auth_failed` (`adminLoginFailureUrl`, a custom passport callback in `routes/admin/auth.js`). Unset, behaviour is upstream's.
- `.github/workflows/upstream-sync.yml` and `.github/scripts/upstream-sync.sh` (fork-only): weekly merge of upstream `main` into `sync/upstream` with a pull request against `main`; conflicts and refused pushes open an issue. Optional secret `UPSTREAM_SYNC_TOKEN` (fine-grained PAT: Contents, Pull requests, Issues, Workflows read and write) lets CI run on the pull request and lets merges that touch upstream workflows be pushed.
- Tenant host check (`packages/api/src/middleware/tenant.ts`): with `TRUST_TENANT_HEADER=true` and the optional `TENANT_HEADER_MATCH_USER=true`, an authenticated request whose user belongs to another tenant than the proxy's `X-Tenant-Id` gets 403. Unset, behaviour is upstream's.
- Admin user deletion (`packages/api/src/admin/deletion.ts`, routed in `api/server/routes/admin/users.js`): with `ADMIN_USER_DELETION=true`, upstream's existing admin erasure handler is reachable as `DELETE /api/admin/users/:id` (capability `MANAGE_USERS`, within the admin's tenant). Unset, the route answers 404 as upstream leaves it unrouted.
- Admin balance API (`packages/api/src/admin/balance.ts`, routed in `api/server/routes/admin/users.js`, audit action `user.balance_updated` in `packages/data-schemas/src/types/admin.ts`): `GET` (`READ_USERS`) and `PUT` (`MANAGE_USERS`) `/api/admin/users/:id/balance` read and set the credit balance of a user in the admin's tenant; upstream sets balances only through `config/set-balance.js`.
- Model catalog lock (`packages/api/src/admin/catalog.ts`, checked in the PUT, PATCH and tombstone handlers of `packages/api/src/admin/config.ts`, switched in `api/server/routes/admin/config.js`): with `ADMIN_CONFIG_CATALOG_LOCK=true`, admin config writes may set `endpoints` only to narrow `librechat.yaml`'s custom endpoints (`name` plus `models.default` from the catalog list), may set `mcpServers` (or `mcpConfig`) only for `librechat.yaml`'s servers and only their booleans `enabled` and `chatMenu` (issue codes `catalog_unknown_mcp_server`, `catalog_field_locked`; tombstones under these sections only for those two fields), and may not reference environment variables anywhere. Unset, behaviour is upstream's.
- MCP file outputs (`fileOutputs` in the server schema of `packages/data-provider/src/mcp.ts`, context `mcp_output` in `FileContext`, parsed and saved by `packages/api/src/mcp/files.ts`, policy passed from `callTool` in `packages/api/src/mcp/MCPManager.ts` to `formatToolContent` in `parsers.ts`, saved by `saveMCPFileOutput` in `api/server/services/Files/process.js` from both tool-end callbacks in `api/server/controllers/agents/callbacks.js`): an admin-defined MCP server with `fileOutputs: true` (or `{ mimeTypes, maxBytes }`; defaults PDF, XML, CSV, OOXML, ZIP and 10 MB) has each embedded `resource` with a base64 `blob` of an allowed type stored through the document file strategy with the user's retention and attached under the reply as a download (artifact key `mcp_files`), and the model reads one line instead. User-created servers never get it, and the catalog lock keeps tenants from setting it. Unset, behaviour is upstream's.
- Per-scope MCP server switch (`enabled` in the server schema of `packages/data-provider/src/mcp.ts`, decided in `packages/api/src/mcp/registry/enabled.ts`, applied in `ensureConfigServers`, `getAllServerConfigs` and `getServerConfig` of `packages/api/src/mcp/registry/MCPServersRegistry.ts`): a config document (tenant, group or role) with `mcpServers.<name>.enabled: false` hides that server from its users in the server and tool lists, the agent builder, tool loading and execution, and the server is not inspected for it; a document of higher priority can set `true` again, so `enabled: false` in `librechat.yaml` makes a server opt-in per tenant. User-created servers are never affected. Unset, behaviour is upstream's.
- MCP call context (`packages/api/src/mcp/callContext.ts`, schema field in `packages/data-provider/src/mcp.ts`, wired in `packages/api/src/mcp/MCPManager.ts` and `api/server/services/MCP.js`): an admin-defined MCP server with `callContext: true` receives the turn's model, saved agent id, conversation id and message id in each `tools/call` request's `_meta` under `librechat/context`. Unset, behaviour is upstream's.
- Custom domains (`packages/api/src/middleware/tenantOrigin.ts`, read in `getTenantDomains` of `packages/api/src/auth/openid/tenant.ts`, mounted in `api/server/index.js` and `api/server/experimental.js`): with `TRUST_TENANT_HEADER=true`, a request whose trusted proxy sends `X-Tenant-Origin` (an http(s) origin) uses that origin as the tenant's client and server URL (OpenID callback, redirects, `serverDomain`) instead of the `TENANT_DOMAIN_*` templates. Unset, behaviour is upstream's.
- Platform model catalog (`packages/data-schemas/src/methods/platformCatalog.ts`, `packages/api/src/platform/`, hook `loadTenantEndpoints` in `packages/api/src/app/service.ts`, wired in `api/server/services/Config/app.js` and `platformCatalog.js`, routes `api/server/routes/platform.js` and `api/server/routes/admin/catalog.js`, audit actions `catalog.*` in `packages/data-schemas/src/types/admin.ts`): the operator API (`PLATFORM_API_TOKEN`, `/api/platform`) stores provider endpoints with encrypted keys and assigns them per tenant with a subset of their models; a tenant the operator opts in (`byok`) adds endpoints with its own key through `/api/admin/catalog`. A provider with `allTenants: true` (`PUT /api/platform/providers/:name`, method `findCatalogProviders`) reaches every tenant with all its models, without an assignment or catalog document; tenant admins narrow its models in their config, and it cannot be deleted until the flag is off (409 `provider_for_all_tenants`). With `ADMIN_CONFIG_CATALOG_LOCK=true` they join the tenant's base config as tenant-scoped custom endpoints, with the provider's `dropParams` (default `['user']`, which Mistral and Azure AI Foundry models reject). Unset, behaviour is upstream's.
- Operator admin role switch (`packages/api/src/platform/admins.ts`, routed in `api/server/routes/platform.js`): `PUT /api/platform/tenants/:tenantId/admins/:subject` with `{ admin, email? }` (`PLATFORM_API_TOKEN`) sets the tenant user with that `openidId` to `ADMIN` or back to `USER` at once (other roles untouched, cached auth documents evicted) instead of at the next OpenID sign-in, and records `role.member_added`/`role.member_removed` in the tenant's audit chain with the operator as actor. Unset token, the route answers 404.
- MCP tool policy (`packages/api/src/platform/toolPolicy.ts`, `packages/data-schemas/src/methods/mcpToolPolicy.ts`, wired in `api/server/services/platformToolPolicy.js`, routed in `api/server/routes/platformMcp.js` and `api/server/routes/admin/mcpTools.js`, audit action `mcp_tool.policy_updated`): the platform's MCP servers register their tools through `/api/platform/mcp` (`PLATFORM_MCP_TOKEN`) and read a user's tool modes there; tenant admins set `off`, `allow` or `confirm` per tool for the tenant and per group (`/api/admin/mcp-tools`). The tool approval hook module `api/server/services/platformToolPolicyHook.js`, listed in `endpoints.agents.toolApproval.hooks`, denies `off` and asks before `confirm` tools. Unset, behaviour is upstream's.
- Tenant deletion (`packages/api/src/platform/purge.ts`, `packages/data-schemas/src/methods/tenantPurge.ts`, wired in `api/server/services/platformTenants.js` with the erasure resolver of `routes/admin/users.js`, route `DELETE /api/platform/tenants/:tenantId` in `api/server/routes/platform.js`, audit action `tenant.purged`): the operator API erases every user of a tenant through the user erasure cascade and then deletes every document with the tenant's id; the append-only audit log stays. Needs `PLATFORM_API_TOKEN`; unset, behaviour is upstream's.
- Tenant branding (`packages/data-provider/src/branding.ts`, field `interface.branding` in `configSchema`, kept by `packages/data-schemas/src/app/interface.ts`, sent before login by `packages/api/src/app/interface.ts`, applied by `packages/api/src/app/branding.ts` in `api/server/routes/config.js`, shown by `client/src/components/Auth/AuthLayout.tsx` and `client/src/utils/favicon.ts`, badge source read lazily in `client/src/hooks/Conversations/useUnseenBadge.ts`): a config document can set the app title, sign-in logo, favicon and footer (an `https:` URL or base64 `data:image` of at most 128 KB). Unset, behaviour is upstream's.
- OpenID group sync (`packages/api/src/auth/openid/groups.ts`, `packages/data-schemas/src/methods/groupSync.ts`, one call in `api/strategies/openidStrategy.js`, group source `oidc` added to the group schema, types, `accessPermissions.ts` and the admin groups filter): with `OPENID_GROUPS_CLAIM`, each OpenID sign-in makes the user's memberships in their identity provider's groups (`oidc` groups, `idOnTheSource` `<provider>:<group>`) match the claim, creating missing groups. Unset, behaviour is upstream's.
- Admin usage API (`packages/data-schemas/src/methods/tenantUsage.ts`, `packages/api/src/admin/usage.ts`, routed in `api/server/routes/admin/usage.js`): `GET /api/admin/usage?days=7|30|90` (capability `READ_USAGE`, which upstream defines but does not use) returns the caller's tenant's active users, messages, conversations and tokens per day and per model, aggregates only, for the admin app's dashboard. `GET /api/admin/usage/pricing` (`READ_USAGE`, `packages/api/src/admin/pricing.ts`) returns `{ models: [{ endpoint, model, prompt, completion }] }` in USD per 1M tokens for every model of the tenant-wide config, whatever `interface.contextCost` says.
- Meilisearch sync under strict tenant isolation (`api/db/index.js`): the startup index sync (`indexSync`) runs in `runAsSystem`, because it reads every tenant's messages and conversations and `TENANT_ISOLATION_STRICT=true` refuses that without a tenant. Searches stay filtered by user.
- Custom endpoints without models (`hasCustomModels` in `packages/api/src/endpoints/custom/config.ts`, used by `loadCustomEndpointsConfig` and `createLoadConfigModels` in `packages/api/src/endpoints/config/models.ts`): a custom endpoint whose `models.default` is empty and that fetches no models is left out of the endpoint and model lists, so a tenant or group narrowing it to no models switches it off. Upstream shows it as a provider without models.

## Environment

- Node 24.16.0 (see `.nvmrc`) and npm 11. MongoDB is required.
- Local setup: `bash .claude/scripts/bootstrap-env.sh` (creates `.env` with fresh dev secrets), `bash .claude/scripts/dev-services.sh up` (MongoDB in Docker), `npm ci`, `npm run build:packages`, then `npm run backend:dev` and `npm run frontend:dev`.
- Cloud sessions do the same automatically through the SessionStart hook (`.claude/scripts/cloud-session-start.sh`). The environment itself is set up as described in `.claude/cloud-environment/README.md`.
- Never read or print `.env`.
- `api` and `data-schemas` tests use `mongodb-memory-server`, which downloads a MongoDB binary on first run. If that fails in a cloud session, it is a network allowlist problem, not a code bug.
- Lighthouse and Playwright e2e are not set up in cloud sessions. Run them only when asked, and when `AGENTS.md` requires one that you cannot run, say so in your report.
- Upstream's `.gitignore` ignores `/.claude/` and `CLAUDE.md` (only `.claude/skills` is tracked, force-added). The files here were added the same way, so a new file under `.claude/` needs `git add -f`.
- The cloud VM has about 4 vCPU and 16 GB RAM. The client build can use up to 8 GB of heap, so do not run it in parallel with the full test suites.
